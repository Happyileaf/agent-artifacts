# 阶段 4—6：异步化、领域边界与微服务拆分

本篇关注商城业务从“一个请求内完成所有事”发展到跨模块协作、异步任务和独立服务的过程。

## 阶段 4：异步化——让交易主链路更短、更可靠

### 4.1 业务背景

商城开始做促销活动。用户下单后，系统除了创建订单和处理库存，还要：
- 发送短信、邮件或站内通知。
- 更新积分和会员成长值。
- 记录营销活动数据。
- 更新商品销量。
- 通知仓库系统。
- 生成经营分析数据。

如果所有动作都同步串行执行，接口耗时会变长；通知服务暂时不可用，也可能拖慢下单。部分任务失败后还需要人工补偿。

### 4.2 同步与异步的边界

不是所有操作都能异步化。订单创建时必须完成的价格校验、库存预占和订单持久化，仍属于交易主流程。短信通知和分析数据更新通常可以异步执行。

\`\`\`mermaid
flowchart TB
    U["用户提交订单"] --> API["订单应用"]
    API --> TX["事务：创建订单 + 库存预占"]
    TX --> DB[("业务数据库")]
    TX --> ACK["返回下单结果"]
    TX --> EVT["发布订单已创建事件"]
    EVT --> MQ[("消息队列")]
    MQ --> N["通知消费者"]
    MQ --> S["销量/积分消费者"]
    MQ --> W["履约消费者"]
\`\`\`

### 4.3 为什么需要消息队列

消息队列（RabbitMQ、Kafka、云消息服务等）可以帮助系统：
- 将生产者和消费者解耦。
- 缓冲流量尖峰，避免下游被瞬间打满。
- 让非核心操作异步执行。
- 支持重试、消费进度和失败消息处理（具体语义依产品而异）。

但消息队列不是“发出去就一定成功”。需要处理消息丢失、重复投递、消费失败、顺序要求和积压。

### 4.4 数据库提交与消息发布的一致性

一个常见错误是：先提交订单事务，再发送消息。如果进程在两步之间崩溃，订单已经存在，但消息没有发出。

可以使用 Transactional Outbox：
1. 在同一个数据库事务里写入订单和待发布事件记录。
2. 独立发布器扫描 Outbox，将事件发送到消息队列。
3. 发布成功后标记事件状态。
4. 消费者按事件 ID 做幂等处理。

\`\`\`mermaid
sequenceDiagram
    participant O as 订单服务
    participant DB as 订单数据库
    participant P as Outbox 发布器
    participant MQ as 消息队列
    participant C as 消费者
    O->>DB: 事务写入订单 + Outbox 事件
    DB-->>O: 提交成功
    P->>DB: 读取待发布事件
    P->>MQ: 发布事件
    MQ-->>P: 确认接收
    P->>DB: 标记已发布
    MQ->>C: 投递事件
    C->>C: 幂等处理
\`\`\`

### 4.5 消费者必须考虑幂等

消息系统常见的是至少一次投递语义，消费者可能收到重复消息。比如同一笔订单的“支付成功”事件重复到达，不能重复增加积分或重复触发发货。

可采用：
- 业务唯一键或事件 ID 去重。
- 数据库唯一约束。
- 状态机条件更新，例如仅允许待支付转为已支付。
- 对外部副作用使用幂等请求号。

不要把“消息只消费一次”当成默认前提。

### 4.6 定时任务与延迟任务

订单超时未支付自动关闭，是典型定时业务：
- 创建订单时记录过期时间。
- 到期后触发关闭逻辑。
- 关闭时检查订单仍处于待支付状态。
- 释放预占库存。
- 对并发支付回调与关单竞态做状态条件保护。

可以从数据库扫描、任务调度器、延迟消息等方案中选择。规模小先用可靠的定时任务即可，不必一开始引入专门调度平台。

### 4.7 本阶段验收

- 同步链路只保留必须同步完成的业务。
- 每类消息有明确的生产者、消费者和事件契约。
- 消息发布可靠性有方案。
- 消费者具备幂等、重试和失败处理能力。
- 有消息积压、消费延迟和失败率监控。

## 阶段 5：领域边界——先把单体内部的业务边界理清楚

### 5.1 业务背景

商城增加多仓库、多商家、促销、退款和售后。商品、库存、订单、支付之间的业务规则越来越复杂。

例如：
- 订单需要读取商品价格，但不能随意修改商品域的数据。
- 库存需要处理预占、扣减、释放和盘点。
- 支付需要处理支付渠道回调、退款和对账。
- 订单需要协调支付和履约状态，但不应该把所有规则写在一个巨大 OrderService 中。

团队开始按业务域分工。此时最重要的是明确业务边界和数据所有权。

### 5.2 模块化单体与领域驱动设计

可以按领域组织系统：
- 商品域：商品、SKU、类目、上下架。
- 库存域：仓库、库存余额、预占记录。
- 订单域：订单生命周期、订单明细和状态机。
- 支付域：支付单、退款、渠道对账。
- 营销域：优惠券、促销规则和优惠计算。

领域驱动设计（DDD）提供统一语言、限界上下文、聚合、领域事件等建模工具。它不是必须完整照搬的一套框架，而是帮助团队处理复杂业务模型的方法。

这张图表达的是业务职责和协作关系，不意味着每个方框都必须是一个独立进程。它们完全可以先存在于同一个单体应用中。

### 5.4 数据所有权的重要性

一个模块可以通过接口访问另一个模块的数据，但不应随意直接修改对方的核心表。

例如订单需要商品信息时，可以通过商品模块提供的接口获得下单快照；订单创建后，订单明细保存成交时的商品名称、SKU、单价和优惠分摊。

领域边界清楚后，未来是否拆服务才有可操作的依据。

### 5.5 为什么要先模块化再拆分

如果单体内部模块边界不清，拆分后会出现：
- 服务之间频繁互相调用。
- 一个业务变更需要多个团队同时发布。
- 数据库表被多个服务共同写入。
- 业务事务跨越多个服务。
- 故障排查必须跨越大量网络调用。

先在单体内建立边界，可以以较低成本验证边界是否合理。

## 阶段 6：微服务——当独立部署和独立扩缩容成为真实需求

### 6.1 业务背景

商城进入快速增长期：
- 商品搜索和商品详情访问量很高，但订单写入量相对稳定。
- 支付团队需要频繁发布渠道适配功能。
- 库存团队需要独立处理促销期间的高并发。
- 多个团队在同一个单体仓库中频繁冲突。
- 某些模块故障会拖垮整个应用。
- 一个模块扩容时，必须连同整个单体一起扩容。

这些问题说明，拆分可能带来明确收益。

### 6.2 拆分的判断条件

至少应有一项强动机：
- 需要独立扩缩容，资源模型差异明显。
- 需要独立发布，团队交付节奏不同。
- 需要隔离故障或安全边界。
- 模块拥有稳定的业务边界和数据所有权。
- 单体的协作成本已经高于分布式系统的额外成本。

“代码文件很多”或“项目已经很大”本身不是充分理由。

### 6.4 服务拆分后新增的基础设施

| 新问题 | 常见能力 | 为什么出现 |
|---|---|---|
| 客户端不应知道内部服务地址 | API Gateway | 统一入口、路由、认证、限流 |
| 服务实例动态变化 | 服务发现 | 实例扩缩容和故障替换 |
| 服务间调用 | HTTP / gRPC / RPC | 跨进程通信 |
| 服务配置分散 | 配置中心或集中配置管理 | 统一变更和环境管理 |
| 服务间身份验证 | 服务身份、mTLS、授权策略 | 防止内部接口被任意调用 |
| 故障相互传播 | 超时、重试、熔断、隔离 | 控制级联故障 |
| 多服务日志难关联 | Trace ID、分布式追踪 | 还原跨服务请求 |
| 多服务数据更新 | Saga、Outbox、补偿 | 跨服务事务无法依赖单库 ACID |

并不是所有项目都需要独立 API Gateway、注册中心和配置中心产品。托管平台、服务网格或云服务可能已经提供部分能力。

### 6.5 数据库拆分与数据所有权

微服务架构强调服务对自身数据负责。常见方向是每个服务拥有自己的逻辑数据库或 Schema，避免多个服务共同写同一组业务表。

这不代表一开始就必须每个服务一台数据库服务器。可以在物理资源上共享数据库集群，但要明确独立 Schema、账号权限、迁移责任和访问边界。

跨服务查询不能再随意做 SQL Join。可以通过：
- 服务 API 查询。
- 事件驱动构建读模型。
- 数据仓库或分析平台。
- 搜索索引或专门查询模型。

### 6.6 跨服务业务流程：订单、库存和支付

订单创建可能跨订单、库存和支付多个服务。传统单数据库事务不能覆盖多个独立数据库。

一种常见方案是 Saga：
1. 订单服务创建待确认订单。
2. 库存服务预占库存。
3. 支付服务创建支付单。
4. 全部成功后订单进入待支付。
5. 任一步骤失败，执行对应补偿，例如释放库存、关闭订单。

补偿不是简单回滚数据库。已经发生的外部副作用可能无法撤销，需要定义业务补偿动作和人工介入路径。

### 6.7 微服务的代价

- 网络调用存在延迟和失败。
- 服务数量增加，部署和监控更复杂。
- 本地调试和集成测试难度提高。
- 数据一致性和事务边界更复杂。
- 版本兼容和接口治理成为日常工作。
- 需要更成熟的值班、发布和故障处理能力。

### 6.8 渐进式拆分，而不是一次性重写

可以采用 Strangler Fig（绞杀者）模式：
1. 先明确某个模块边界。
2. 为模块定义稳定接口。
3. 新流量逐步路由到新服务。
4. 将该模块的数据写入责任迁移到新服务。
5. 校验新旧行为和数据。
6. 完成切流后删除旧实现。

优先选择边界清楚、独立扩缩容收益明确、跨域事务相对少的模块。不要一次性把所有模块拆出去。

### 6.9 阶段验收

- 每个服务有明确业务责任和数据所有权。
- 服务间接口有版本和兼容策略。
- 超时、重试、幂等和故障隔离有统一原则。
- 跨服务业务流程有状态跟踪和补偿机制。
- 有服务级指标、日志和分布式追踪。
- 团队具备独立发布和生产运维能力。

### 6.10 本篇小结

异步化解决请求链路和任务解耦问题；领域建模解决业务复杂度和边界问题；微服务解决独立部署、扩缩容和组织协作问题。三者并非同一件事，也不必同时发生。
