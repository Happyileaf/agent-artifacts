# 服务端系统架构演化指南

> 以一个持续成长的在线商城为例，理解服务端系统如何从简单应用演化为成熟的大型服务端平台。

## 1. 文档目标

本文不是技术名词清单，也不是要求所有系统最终都采用微服务、Kubernetes 或分库分表。本文关注的是一条因果链：

**业务发生变化 → 原有方案出现具体问题 → 识别真正的瓶颈 → 选择合适的改造 → 引入新的能力和复杂度。**

通过同一个商城案例，理解前端、后端、数据库、缓存、消息队列、搜索、微服务、容器平台、可观测性和高可用体系分别在什么情况下出现，以及它们之间的关系。

读完后，读者应能回答：
- 一个最初只有 Web、API 和数据库的商城，为什么会逐渐出现更多服务和基础设施？
- 每次架构变化具体解决了什么业务问题？
- 新方案带来了哪些新的故障模式、运维成本和一致性问题？
- 哪些能力可以提前建设，哪些应该等真实需求出现后再引入？
- 面对一个实际系统，如何判断下一步最值得做的架构改造？

## 2. 案例背景：一家持续成长的在线商城

假设我们建设一家销售日用品和数码产品的在线商城。初期只有一个小团队，业务从单一品类起步，之后逐步发展为多品类、多仓库、多商家、多渠道经营的平台。

### 2.1 核心业务

| 业务域 | 主要职责 | 典型操作 |
|---|---|---|
| 用户 | 注册、登录、账户资料、收货地址 | 登录、修改资料 |
| 商品 | SPU/SKU、类目、属性、价格、上下架 | 浏览商品、查询详情 |
| 库存 | 仓库库存、可售库存、预占和释放 | 查询库存、扣减库存 |
| 购物车 | 用户选购的商品及数量 | 加购、修改数量 |
| 订单 | 订单创建、状态流转、取消、售后 | 提交订单、查询订单 |
| 支付 | 支付单、支付渠道、退款、对账 | 发起支付、接收支付结果 |
| 履约 | 仓库、拣货、发货、物流轨迹 | 出库、发货 |
| 营销 | 优惠券、满减、促销活动 | 计算优惠、领取优惠券 |
| 搜索 | 商品检索、筛选、排序 | 关键词搜索 |
| 运营 | 商品管理、订单管理、数据报表 | 运营后台操作 |

### 2.2 一笔订单的典型业务过程

1. 用户浏览商品，查看价格和可售库存。
2. 用户将商品加入购物车。
3. 用户提交订单，服务端校验商品状态、价格、优惠和收货地址。
4. 系统预占库存并创建待支付订单。
5. 用户跳转支付渠道完成付款。
6. 支付渠道异步通知商城支付结果。
7. 商城确认支付，订单进入待发货状态。
8. 仓库拣货、出库，物流信息回传。
9. 用户收货，订单完成。
10. 系统处理通知、积分、销售统计等后续任务。

这条链路贯穿全文。后续引入的数据库事务、缓存、消息队列、服务拆分、幂等、分布式事务和可观测性，都可以在这条业务链路中找到实际动机。

## 3. 演化总览

系统并不是按照固定的规模阈值升级。下表描述的是可能出现的演化路径，而非必须执行的阶段清单。

| 阶段 | 业务状态 | 主要矛盾 | 典型架构变化 |
|---|---|---|---|
| 1. 最小可用系统 | 单一商城、少量用户 | 先把交易闭环跑通 | 前端 + 单体后端 + 关系型数据库 |
| 2. 单体工程化 | 功能增加、多人开发 | 代码耦合、质量难保证 | 分层、模块化、测试、CI/CD |
| 3. 单体性能优化 | 访问增长、读多写少 | 数据库和静态资源压力 | 索引、缓存、对象存储、CDN |
| 4. 异步化 | 下单后任务增多 | 请求链路过长、任务易丢 | 消息队列、任务调度、Outbox |
| 5. 领域边界清晰 | 业务规则复杂、团队分工 | 模块边界和数据责任不清 | 模块化单体、领域建模 |
| 6. 服务拆分 | 独立扩缩容和发布成为刚需 | 单体部署耦合、故障影响面大 | 微服务、网关、服务发现、RPC |
| 7. 大规模数据与流量 | 热点、峰值、数据量增长 | 单库、缓存和同步链路承压 | 读写分离、分片、搜索、限流 |
| 8. 云原生平台 | 服务和团队数量增长 | 部署治理和资源利用复杂 | 容器、编排、自动化交付、可观测性 |
| 9. 成熟大型系统 | 多地域、强可靠性要求 | 故障恢复、合规、成本与治理 | 容灾、多活/异地灾备、平台工程、SRE |

### 3.1 架构形态变化

\`\`\`mermaid
flowchart TD
    A["阶段 1：Web / API / 单库"] --> B["阶段 2：工程化单体"]
    B --> C["阶段 3：单体 + 缓存 / CDN"]
    C --> D["阶段 4：单体 + MQ / 异步任务"]
    D --> E["阶段 5：模块化单体 / 领域边界"]
    E --> F["阶段 6：微服务 / 服务治理"]
    F --> G["阶段 7：数据分片 / 搜索 / 流量治理"]
    G --> H["阶段 8：容器平台 / DevOps / 可观测性"]
    H --> I["阶段 9：高可用 / 容灾 / 平台化"]
\`\`\`

真实系统可能跳过某些阶段，也可能在某个阶段停留多年。比如业务规模不大但合规要求很高的系统，可能很早就需要审计、备份和灾备；一个业务复杂但流量不大的系统，可能长期适合模块化单体。

## 5. 重要前提

### 5.1 技术不是目标

Redis、Kafka、Elasticsearch、Kubernetes 都不是架构成熟度的勋章。若数据库加索引已经满足性能目标，就不必为了使用缓存而增加缓存一致性问题；若单体可以独立开发和部署，就不必为了流行趋势拆成微服务。

### 5.2 规模不是唯一变量

是否需要演化，至少取决于：
- 业务复杂度：规则、状态、流程、外部依赖是否增多。
- 流量特征：平均流量、峰值、突发流量、热点是否变化。
- 数据规模：数据量、增长速度、访问模式和保留周期。
- 团队规模：并行开发、发布频率、代码所有权和协作成本。
- 可靠性目标：允许的停机时间、数据丢失范围和恢复时间。
- 合规与安全：隐私、审计、权限、数据驻留等要求。

### 5.3 每次演化都要计算总成本

新架构不仅有开发成本，还包括运行成本、排障成本、数据迁移成本、团队认知成本和故障处理成本。复杂度必须由收益来证明。

### 5.4 本文中的技术栈是代表性选项

文中会使用常见技术举例，例如 PostgreSQL/MySQL、Redis、RabbitMQ/Kafka、OpenSearch/Elasticsearch、Docker、Kubernetes。它们代表解决问题的一类方案，不意味着唯一选择，也不意味着需要同时采用同类产品。
