## 1. 产品概述

### 1.1 产品背景

本项目旨在实现一个基于浏览器的多人在线会议与实时聊天室。用户无需注册或登录，通过创建会议、分享邀请链接即可邀请其他人加入，在浏览器中完成多人音视频交流和实时文字沟通。

项目同时提供 WebRTC 技术监控面板，用于观察音视频通信建立和运行过程中的关键状态与数据，帮助开发者理解 WebRTC 的核心工作原理。

### 1.2 产品目标

1. 实现无需注册的多人在线会议。
2. 支持通过会议邀请链接加入指定会议。
3. 支持多人实时音视频通信。
4. 支持会议内实时文字聊天。
5. 提供可观察、可理解的 WebRTC 技术监控信息。
6. 通过完整业务场景实践 WebRTC、实时通信和浏览器媒体能力。

### 1.3 项目定位

这是一个以学习和技术实践为主要目的的项目，不以生产级会议产品为目标。

需求重点聚焦于核心会议业务流程、多人数音视频和文字聊天、会议成员状态与会议生命周期，以及 WebRTC 连接建立、媒体传输和网络状态的可观察性。

不为生产级场景引入复杂的账号体系、容灾体系、运维平台、性能 SLA 或高级会议管理能力。

### 1.4 目标用户

- 希望快速发起临时音视频交流的用户。
- 参与会议并进行实时沟通的用户。
- 希望通过实际运行观察 WebRTC 工作过程的开发者和学习者。

### 1.5 核心产品流程

~~~text
打开 Web 应用
    ↓
创建会议 / 通过邀请链接加入
    ↓
输入昵称并授权设备
    ↓
预览音视频并选择设备
    ↓
进入会议
    ↓
多人音视频交流 + 实时文字聊天
    ↓
查看 WebRTC 技术监控信息
    ↓
离开会议 / 会议结束
~~~

## 2. 用户身份与核心规则

### 2.1 用户身份

1. 用户无需注册或登录。
2. 用户进入会议前需要设置昵称。
3. 昵称用于会议内展示，不承担身份认证职责。
4. 用户加入会议时，系统为其分配唯一的会议参与者身份标识。
5. 参与者身份标识仅在当前会议的参与关系中有效，不要求跨会议保持一致。
6. 创建会议的用户为会议创建者，创建者身份与普通参会者身份有所区别。

### 2.2 参与者身份与恢复规则

1. 参与者身份标识与当前会议参与关系绑定，不能仅通过昵称判断参与者身份。
2. 浏览器刷新或短暂网络中断时，需要保留恢复原参与者身份所需的信息。
3. 参与者在意外断线后的 30 秒等待期内重新进入会议，应恢复原有参与者身份。
4. 创建者在等待期内恢复后，仍保留原会议创建者身份及会议生命周期控制权。
5. 超过等待时间后，原参与者身份不可继续恢复。
6. 本项目不建立账号体系，也不要求参与者身份跨会议持久化。

### 2.3 会议人数规则

1. 单个会议最多允许 10 名有效参会者，创建者计入人数。
2. 处于意外断线重连等待期的参与者仍占用会议名额。
3. 当会议已有 10 名有效参会者时，第 11 名用户无法加入。
4. 人数已满时，应向用户展示明确提示：会议人数已满。
5. 不实现排队、候补或自动清理等待成员等机制。

### 2.4 会议基本规则

1. 一个会议具有唯一的会议标识和邀请链接。
2. 用户通过有效邀请链接进入对应会议。
3. 会议创建者与普通参会者具有不同的生命周期规则。
4. 会议内参会者可以查看当前成员列表及成员音视频状态。
5. 会议内成员之间可以进行实时文字沟通。

## 3. 核心用户场景

### 3.1 创建会议

1. 用户打开 Web 应用。
2. 用户选择创建会议。
3. 系统创建一个新的会议。
4. 创建者设置昵称并进入设备准备流程。
5. 创建者完成设备授权和预览后进入会议。
6. 系统提供会议邀请链接，创建者可以复制并分享给其他用户。

### 3.2 加入会议

1. 用户通过邀请链接打开会议页面。
2. 系统识别邀请链接对应的会议。
3. 用户输入昵称。
4. 用户完成必要的设备授权和设备准备。
5. 用户加入会议。
6. 会议内其他成员能够看到新成员加入及其当前状态。

### 3.3 会议内音视频交流

1. 用户进入会议后可以查看其他参会者。
2. 用户可以开启或关闭自己的麦克风。
3. 用户可以开启或关闭自己的摄像头。
4. 其他参会者能够感知成员音视频状态变化。
5. 成员之间能够进行实时音频和视频交流。
6. 单个成员关闭自己的音视频设备，不应导致其他成员的通信被中断。

### 3.4 会议内文字聊天

1. 会议成员可以在会议过程中发送文字消息。
2. 其他当前在线的会议成员可以实时接收消息。
3. 新加入会议的成员不接收其加入之前产生的聊天历史消息。
4. 聊天内容仅属于当前会议场景。

### 3.5 查看技术监控信息

1. 用户可以在会议过程中打开技术监控面板。
2. 面板展示当前浏览器实际能够观测到的信令、连接、ICE 和媒体传输信息。
3. 用户可以查看连接状态变化及关键事件。
4. 用户可以查看当前可获取的网络和媒体统计数据。
5. 监控数据用于理解当前客户端的通信过程，不承诺展示整个会议的全局网络拓扑。

### 3.6 离开会议与会议结束

1. 普通参会者主动离开会议后，不影响其他成员继续会议。
2. 创建者主动离开会议时，会议立即结束。
3. 普通参会者意外断线时，进入 30 秒重连等待期；等待期内恢复则继续以原身份参与，超过等待期则视为离开。
4. 创建者意外断线时，会议进入创建者重连等待状态。等待期间已加入成员可以继续交流，但不允许新成员加入。
5. 创建者在 30 秒内恢复，会议恢复正常；超过 30 秒未恢复，会议结束。
6. 所有成员均主动离开，或所有意外断线成员均已超过重连等待期且会议中不再有有效成员时，会议结束。

## 4. 功能需求

### 4.1 创建与加入会议

#### 创建会议

- 提供创建会议入口。
- 创建成功后生成唯一会议标识。
- 创建者自动成为该会议的创建者和首位参会者。
- 创建者进入设备准备流程。
- 提供可复制的会议邀请链接。

#### 加入会议

- 支持通过邀请链接加入会议。
- 能够识别邀请链接对应的会议。
- 加入前要求用户设置昵称。
- 会议不存在或已结束时，应提示用户无法加入。
- 会议人数达到上限时，应提示“会议人数已满”。
- 创建者处于意外断线等待状态时，暂时禁止新成员加入。

### 4.2 设备准备与预览

- 用户进入会议前可以进行设备准备。
- 支持申请摄像头和麦克风访问权限。
- 支持预览本地摄像头画面。
- 支持选择可用的摄像头设备。
- 支持选择可用的麦克风设备。
- 用户可以在进入会议前确认设备是否正常工作。
- 用户拒绝授权或设备不可用时，应向用户提供明确提示。

### 4.3 会议内音视频控制

- 支持开启和关闭本地麦克风。
- 支持开启和关闭本地摄像头。
- 能够正确展示本地音视频开关状态。
- 能够将成员音视频状态变化同步给其他参会者。
- 能够接收其他参会者的音视频媒体流。
- 能够展示其他参会者的视频画面。
- 能够播放其他参会者的音频。
- 成员关闭摄像头后，其他成员应能感知其视频状态变化。
- 成员关闭麦克风后，其他成员应能感知其音频状态变化。

### 4.4 参会者列表

- 展示当前会议参会者。
- 能够区分会议创建者与普通参会者。
- 展示参会者昵称。
- 展示参会者当前麦克风状态。
- 展示参会者当前摄像头状态。
- 能够感知参会者加入、主动离开及意外断线等状态变化。
- 意外断线等待期内的成员应具有可识别的等待状态。
- 会议人数最多为 10 人，创建者计入人数；等待重连的成员仍占用名额。
- 第 11 名用户加入时应被拒绝，并收到“会议人数已满”的提示。

### 4.5 会议内实时文字聊天

- 提供会议内聊天区域。
- 支持发送文字消息。
- 支持实时接收其他当前会议成员发送的消息。
- 消息应展示发送者昵称和消息内容。
- 消息应按照实际发送顺序展示。
- 新加入会议的成员不接收其加入之前产生的聊天历史消息。
- 不要求实现复杂的消息历史存储和跨会议消息管理。

### 4.6 会议邀请

- 创建会议后生成邀请链接。
- 提供复制邀请链接的操作。
- 其他用户可以通过链接直接进入对应会议的加入流程。
- 邀请链接失效或会议结束时，应提供明确反馈。

### 4.7 会议生命周期管理

#### 主动离开

- 普通参会者主动点击离开后，立即退出会议。
- 普通参会者主动离开不影响其他成员继续交流。
- 创建者主动点击离开后，立即结束会议。
- 会议结束后，其他成员应收到会议结束状态并退出会议。

#### 意外断线与重连

- 网络中断、浏览器刷新或浏览器异常关闭等非主动离开情况，进入意外断线处理流程。
- 意外断线的参与者进入 30 秒重连等待期。
- 普通参会者在等待期内恢复，应恢复原有参与者身份和会议参与关系。
- 普通参会者超过等待期未恢复，视为离开会议。
- 重连等待期内的参与者继续占用会议名额。

#### 创建者意外断线

- 创建者意外断线后，会议进入“创建者重连等待状态”。
- 等待期间，已加入会议的其他成员可以继续交流。
- 等待期间禁止新成员加入。
- 创建者在 30 秒内恢复后，会议恢复正常。
- 创建者超过 30 秒未恢复，会议结束。

#### 会议结束条件

- 创建者主动离开。
- 创建者意外断线超过 30 秒未恢复。
- 所有成员均主动离开。
- 所有意外断线成员均已超过等待期，且会议中不存在有效成员。

本项目不要求实现复杂的生产级容错和多重恢复机制。

### 4.8 WebRTC 技术监控面板

#### 4.8.1 监控目标

技术监控面板用于帮助开发者理解 WebRTC 通信过程，展示当前客户端实际能够观测到的技术状态和数据。

监控数据必须来源于真实的运行状态和浏览器提供的统计信息，不得使用模拟数据填充真实监控指标。

#### 4.8.2 监控对象组织

监控信息分为三个层次：

| 层次 | 主要内容 |
|---|---|
| 会议级 | 当前会议状态、本地设备状态、信令连接状态及信令事件 |
| 连接级 | PeerConnection 状态、ICE 状态、SDP 交换、Candidate 收集与交换、Candidate Pair 和连接事件 |
| 媒体级 | 音视频发送与接收状态、媒体传输统计数据 |

连接级监控以当前浏览器实际存在的 WebRTC 连接为基本对象，并尽可能关联对应的参会者或媒体通信端点。

监控面板只展示当前客户端能够直接观测到的数据，不要求展示整个会议的全局连接拓扑。具体连接对象以实际运行时建立的连接为准。

#### 4.8.3 信令与连接状态

展示当前可获取的信令连接状态和状态变化事件。

展示 PeerConnection 的关键状态，包括：

- signalingState
- connectionState
- iceConnectionState
- iceGatheringState

展示 SDP Offer / Answer 的生成、发送、接收等实际交换过程。

展示 ICE Candidate 的收集、交换和连接检查等实际事件。

#### 4.8.4 ICE 与网络连接信息

- 展示 ICE Candidate 收集和交换事件。
- 展示 ICE 连通性检查过程中的关键状态。
- 展示实际选中的 ICE Candidate Pair。
- 根据实际选中的 Candidate Pair，区分当前连接为直连或中继。
- 展示当前能够获取的 RTT 等连接统计信息。

#### 4.8.5 音视频媒体统计

根据浏览器 WebRTC Stats 实际提供的数据，展示当前可获取的媒体指标，包括：

- 音视频发送和接收状态。
- 发送码率和接收码率。
- 视频分辨率。
- 视频帧率。
- 接收丢包统计及派生丢包率。
- 当前可获取的 RTT。
- 其他与当前媒体传输直接相关且浏览器能够提供的基础统计信息。

#### 4.8.6 数据来源与统计规则

| 数据项 | 数据来源或计算方式 |
|---|---|
| 信令连接状态 | 实际信令连接状态及其事件 |
| PeerConnection 状态 | RTCPeerConnection 状态属性及状态变化事件 |
| ICE 状态 | ICE 状态属性及相关事件 |
| SDP Offer / Answer | 实际信令交换过程 |
| ICE Candidate | 实际 Candidate 收集和交换事件 |
| RTT | WebRTC Stats 中实际可获取的连接统计 |
| 丢包率 | WebRTC Stats 接收统计数据及相邻采样数据 |
| 发送 / 接收码率 | 相邻采样字节数差值除以实际采样时间间隔 |
| 分辨率 | WebRTC Stats 中实际可获取的视频帧尺寸 |
| 帧率 | WebRTC Stats 中实际可获取的视频帧统计 |
| 连接类型 | 实际选中的 ICE Candidate Pair |

统计规则：

1. 原始数据以浏览器 WebRTC API 和 WebRTC Stats 提供的实际数据为准。
2. 动态网络和媒体指标建议每秒采样更新一次。
3. 码率根据相邻两次采样的字节数差值和实际时间间隔计算。
4. 丢包率根据相邻采样的接收数据和丢包统计计算。
5. RTT 展示当前能够获取的实际值。
6. 分辨率和帧率展示实际媒体传输统计。
7. 某项数据暂时无法获取时，应显示“未知”或“不适用”，不得使用模拟值填充。
8. 不要求复杂历史分析、长期数据存储或生产级监控告警。

#### 4.8.7 关键事件时间线

监控面板应能够展示当前客户端实际观测到的关键事件，并按真实发生时间排序。

典型事件包括：

- PeerConnection 创建。
- Offer 生成及发送。
- Answer 接收。
- ICE Candidate 收集。
- ICE Candidate 交换。
- ICE 连通性检查。
- ICE 连接建立。
- 媒体轨道开始传输。
- 连接异常或断开。

事件应尽可能关联到对应的连接对象。上述事件是典型流程，不要求每次严格按照固定顺序出现，以浏览器实际观测结果为准。

### 4.9 异常与状态提示

- 用户拒绝摄像头或麦克风权限时，提供明确提示。
- 摄像头或麦克风不可用时，提供明确提示。
- 会议不存在或已经结束时，提示用户无法加入。
- 会议人数已满时，提示“会议人数已满”。
- 信令连接断开时，能够展示相应状态。
- PeerConnection 或 ICE 连接状态异常时，能够展示相应状态。
- 参与者意外断线时，能够展示重连等待状态。
- 创建者意外断线时，能够展示创建者重连等待状态。
- 会议结束时，能够向其他成员同步会议结束状态。

异常提示聚焦于核心业务流程和技术状态，不要求实现复杂的故障诊断或自动修复系统。

4. 会议邀请链接及复制操作。
5. 实时文字聊天区域。
6. 技术监控面板入口。
7. 离开会议操作。

### 5.6 技术监控面板

- 展示会议级状态。
- 展示连接级状态和关键事件。
- 展示媒体级统计数据。
- 展示关键事件时间线。
- 对无法获取的数据展示未知或不适用状态。

## 6. 本项目明确不做的内容

本项目聚焦于多人音视频会议、实时文字聊天和 WebRTC 技术原理实践，以下内容不纳入本次需求范围：

8. 跨会议聊天历史和持久化消息管理。
9. 生产级多区域容灾和复杂网络恢复体系。
10. 生产级性能 SLA、容量规划和运维告警平台。
11. 复杂监控历史分析和长期数据存储。
12. 本 PRD 不规定具体技术选型、系统架构、开发步骤和项目排期。

## 7. 非功能需求

### 7.1 浏览器与运行环境

- 产品以现代桌面浏览器为主要运行环境。
- 浏览器需要支持项目所依赖的 WebRTC 和媒体设备能力。
- 用户需要通过浏览器授权才能使用摄像头和麦克风。
- 在不支持相关能力或权限不可用时，应提供明确提示。

### 7.2 易用性

- 无需注册或登录即可创建和加入会议。
- 用户可以通过邀请链接快速加入会议。
- 核心操作应清晰可见，包括加入会议、设备控制、聊天和离开会议。
- 关键异常状态应有明确反馈。

### 7.3 多人通信能力

- 单个会议目标人数为 5～10 人。
- 需要支持 10 人同时在线的核心验证场景。
- 需要支持成员独立开启或关闭音视频设备。
- 单个成员退出或发生连接异常，不应直接导致其他成员的通信中断。

### 7.4 技术监控真实性

- 监控数据必须来自真实运行状态和浏览器提供的 WebRTC 统计数据。
- 动态指标应基于实际采样时间计算。
- 无法获取的数据应明确标识，不得使用模拟数据伪装为真实数据。
- 监控面板反映当前客户端可观测范围，不承诺提供会议全局视角。

### 7.5 项目范围约束

- 项目以学习和技术实践为目标。
- 不要求达到商业会议产品的稳定性、可用性或性能标准。
- 不为非核心场景引入复杂的生产级机制。
- 优先保证核心业务流程完整，以及 WebRTC 关键技术过程可观察、可验证。

## 8. 验收标准

### 8.1 创建与加入会议

- [ ] 用户无需注册或登录即可创建会议。
- [ ] 创建会议后能够生成唯一会议标识。
- [ ] 创建者能够获取并复制会议邀请链接。
- [ ] 其他用户能够通过邀请链接加入对应会议。
- [ ] 用户能够设置昵称并完成设备准备。
- [ ] 会议不存在或已结束时，用户能够收到明确提示。

### 8.2 设备准备

- [ ] 用户能够申请摄像头和麦克风权限。
- [ ] 用户能够预览本地摄像头画面。
- [ ] 用户能够选择可用的摄像头设备。
- [ ] 用户能够选择可用的麦克风设备。
- [ ] 权限被拒绝或设备不可用时，能够收到明确提示。

### 8.3 多人音视频通信

核心验收场景 A：10 人同时进行音视频交流。

- [ ] 10 名用户能够同时加入同一个会议，创建者计入人数。
- [ ] 10 名用户均开启摄像头和麦克风时，能够正常进行会议交流。
- [ ] 每名用户能够看到其他 9 名参会者的视频画面。
- [ ] 每名用户能够接收其他 9 名参会者的音频。
- [ ] 参会者列表和音视频状态能够正确同步。

核心验收场景 B：成员独立控制音视频。

- [ ] 10 名用户在线时，部分成员可以关闭摄像头或麦克风。
- [ ] 其他成员能够正确感知对应成员的音视频状态变化。
- [ ] 成员重新开启摄像头或麦克风后，其他成员能够恢复接收相应媒体。
- [ ] 单个成员切换音视频状态不应影响其他成员的正常通信。

核心验收场景 C：成员退出与连接异常。

- [ ] 普通成员主动离开后，其他成员能够继续会议。
- [ ] 普通成员意外断线后，其他成员能够继续会议。
- [ ] 普通成员在 30 秒等待期内恢复后，能够恢复原有参与者身份。
- [ ] 单个成员退出或连接异常，不应直接导致其他成员连接中断。

### 8.4 人数限制

- [ ] 单个会议最多允许 10 名有效参会者，创建者计入人数。
- [ ] 意外断线等待中的成员仍占用会议名额。
- [ ] 已有 10 名有效参会者时，第 11 名用户无法加入。
- [ ] 第 11 名用户能够收到“会议人数已满”的明确提示。

### 8.5 会议生命周期

- [ ] 普通参会者主动点击离开后立即退出会议。
- [ ] 普通参会者主动离开不影响其他成员继续会议。
- [ ] 创建者主动点击离开后，会议立即结束。
- [ ] 普通参会者意外断线后进入 30 秒重连等待期。
- [ ] 普通参会者在等待期内恢复后，能够恢复原参与者身份。
- [ ] 普通参会者超过等待期未恢复后，视为离开会议。
- [ ] 创建者意外断线后，会议进入创建者重连等待状态。
- [ ] 创建者等待期间，已加入成员可以继续交流。
- [ ] 创建者等待期间，新成员无法加入会议。
- [ ] 创建者在 30 秒内恢复后，会议能够继续正常进行。
- [ ] 创建者超过 30 秒未恢复后，会议结束。
- [ ] 所有成员主动离开，或所有意外断线成员等待超时且不存在有效成员后，会议结束。

### 8.6 实时文字聊天

- [ ] 会议成员能够发送文字消息。
- [ ] 当前在线的其他会议成员能够实时收到消息。
- [ ] 消息能够正确展示发送者昵称和消息内容。
- [ ] 消息能够按照实际发送顺序展示。
- [ ] 新加入会议的成员不会收到其加入之前产生的聊天历史消息。

### 8.7 WebRTC 技术监控

- [ ] 监控面板能够按照会议级、连接级和媒体级组织监控信息。
- [ ] 能够识别当前客户端实际存在的 PeerConnection。
- [ ] 能够将连接关联到对应参会者或媒体通信端点（在信息可获取时）。
- [ ] 能够展示真实的信令连接状态和状态变化。
- [ ] 能够展示真实的 PeerConnection 状态变化。
- [ ] 能够展示实际发生的 SDP Offer / Answer 交换事件。
- [ ] 能够展示实际发生的 ICE Candidate 收集和交换事件。
- [ ] 能够展示 ICE 连接建立及异常状态。
- [ ] 能够从浏览器 WebRTC Stats 获取实际可用的媒体统计数据。
- [ ] 发送码率和接收码率基于相邻采样数据及实际时间间隔计算。
- [ ] 丢包率基于实际接收统计数据计算。
- [ ] 能够展示当前可获取的 RTT。
- [ ] 能够展示实际可获取的视频分辨率和帧率。
- [ ] 能够根据实际选中的 ICE Candidate Pair 区分直连和中继。
- [ ] 无法获取的指标展示未知或不适用，不使用模拟数据填充。
- [ ] 关键事件按照真实发生时间排序，并尽可能关联对应连接对象。

### 8.8 异常状态

- [ ] 摄像头或麦克风权限被拒绝时能够提示用户。
- [ ] 摄像头或麦克风不可用时能够提示用户。
- [ ] 会议不存在或已经结束时能够提示用户。
- [ ] 会议人数已满时能够提示用户。
- [ ] 信令连接断开时能够展示相应状态。
- [ ] WebRTC 连接异常时能够展示相应状态。
- [ ] 参与者意外断线时能够展示重连等待状态。
- [ ] 创建者意外断线时能够展示创建者重连等待状态。
- [ ] 会议结束时其他成员能够收到结束状态。

## 11. 部署目标与运行模式

### 11.1 总体部署原则

本项目应支持在一台机器上完整运行。项目所需的 Web 前端、业务服务、实时信令、媒体通信及其他必要组件，可以部署在同一台机器上，不要求依赖多台服务器或复杂的分布式基础设施。

项目采用同一套应用代码和核心业务逻辑，支持不同的运行与访问模式。不同模式主要通过监听地址、访问入口、网络和安全配置进行区分，不应因此维护多套业务实现。

部署设计遵循以下原则：

1. **单机完整运行优先**：开发和演示阶段，优先验证所有必要组件能否在一台机器上完整运行。
2. **浏览器即用**：参会者无需安装独立客户端，只需通过浏览器访问会议链接。
3. **部署方式尽量简单**：优先采用易于本地启动和复现的部署方式，不引入 Kubernetes、复杂集群或生产级运维设施。
4. **运行模式共享代码**：本机开发、局域网演示和公网部署使用同一套应用代码，差异通过运行配置和网络环境处理。
5. **按需引入基础设施**：不因部署模式预先引入非核心数据库、复杂存储或其他基础设施。
6. **保留迁移空间**：当前以单机部署为目标，但模块边界应避免不必要的强耦合，为后续迁移到云服务器或拆分部署保留空间。
7. **明确网络边界**：Web 页面可访问不代表 WebRTC 媒体链路必然可用；部署时还需要考虑信令连接、ICE 协商、UDP 连通性以及必要时的 TURN 中继。

### 11.2 三种运行模式

#### 模式 A：本机开发

所有必要服务运行在开发者自己的计算机上，开发者通过本机地址访问应用。

典型访问方式：

- Web 页面通过 `localhost` 或 `127.0.0.1` 访问。
- 前端、业务服务、信令服务和媒体服务均运行在本机。
- 服务可以直接在操作系统中运行，也可以通过容器方式运行；具体方式由后续技术方案确定。

主要用途：

- 日常功能开发和调试。
- 查看服务日志、排查问题。
- 验证核心业务流程和 WebRTC 技术行为。
- 在单台设备上进行基础功能测试。

模式要求：

1. 项目能够在一台开发机器上启动完整运行所需的服务。
2. 开发者能够通过本机浏览器访问产品。
3. 支持代码修改后的快速反馈和调试。
4. 不要求其他设备能够访问本机服务。
5. 本机开发环境应提供清晰、可复现的启动和停止方式。

#### 模式 B：局域网演示

所有必要服务仍运行在一台机器上，但允许同一局域网内的其他设备通过该机器的局域网地址访问应用。

典型访问方式：

- 由运行服务的机器提供局域网可访问地址，例如 `https://192.168.x.x` 或局域网内可解析的主机名。
- 其他电脑或手机连接同一局域网后，通过该地址打开会议页面。
- 会议链接使用其他设备能够访问的地址生成和分享，不能错误地使用仅对服务端本机有效的 `localhost` 地址。

主要用途：

- 多台真实设备之间的音视频联调。
- 邀请其他局域网用户参与会议演示。
- 验证不同设备、浏览器和媒体设备之间的协作。
- 观察真实网络环境下的 WebRTC 连接情况。

模式要求：

1. 服务应监听适当的网络接口，使局域网内其他设备能够访问。
2. 应明确配置应用访问入口、信令地址和媒体服务对外公布的地址，避免客户端获得不可访问的本机地址。
3. 应根据 macOS 防火墙和实际网络情况开放必要端口。
4. 摄像头和麦克风等浏览器媒体能力通常要求安全上下文。通过局域网 IP 访问时，应配置可信 HTTPS 访问方式，不能假设普通 HTTP 局域网地址一定可用。
5. 应验证信令连接和 WebRTC 媒体链路均可从其他设备建立；仅能打开 Web 页面不视为局域网演示通过。
6. 应考虑局域网内设备之间的网络隔离、无线网络客户端隔离等可能影响连接的问题。

#### 模式 C：公网部署

所有必要服务可以部署在一台具有公网访问能力的服务器上，其他用户通过公开的 HTTPS 会议链接从互联网加入。

典型访问方式：

- 使用公网域名作为统一产品入口。
- 通过 HTTPS 访问 Web 页面。
- 通过配置好的信令和媒体通信地址建立实时连接。
- 根据网络连通性提供 STUN 和必要的 TURN 中继能力。

主要用途：

- 向不同网络环境中的用户分享会议链接。
- 进行跨网络、跨地域的多人会议测试。
- 展示项目完整成果。

模式要求：

1. 其他用户无需安装客户端，只需使用现代浏览器访问有效会议链接。
2. Web 页面和相关浏览器通信入口应满足 HTTPS 安全上下文要求。
3. 公网服务器、防火墙和网络入口应开放实际部署所需的 TCP / UDP 端口。
4. 应验证 ICE Candidate 公布地址、媒体 UDP 连通性和必要的 TURN 中继能力。
5. 会议邀请链接应使用公网用户可访问的域名或地址。
6. 初期允许所有必要组件部署在同一台服务器上，不要求多机部署。
7. 公网部署是项目需要验证的运行模式，不代表本项目承诺生产级 SLA、弹性扩容或高可用能力。

### 11.3 三种模式的关系

| 对比项 | 模式 A：本机开发 | 模式 B：局域网演示 | 模式 C：公网部署 |
|---|---|---|---|
| 服务运行位置 | 开发者本机 | 一台局域网内机器 | 一台具有公网访问能力的服务器 |
| 访问范围 | 当前机器 | 同一局域网设备 | 互联网用户 |
| 典型访问入口 | localhost | 局域网 IP / 主机名 | 公网域名 |
| HTTPS 要求 | localhost 通常可作为安全上下文 | 应配置可信 HTTPS | 必须提供 HTTPS |
| 网络配置重点 | 本机端口和服务启动 | 网卡监听、防火墙、局域网可达性 | DNS、TLS、防火墙、公网媒体连通性 |
| 主要目的 | 开发与调试 | 多设备联调和演示 | 跨网络分享与演示 |

三种模式不是三套独立系统，也不要求分别开发产品功能。模式 A 是默认开发方式；需要多设备参与时使用模式 B；需要互联网用户访问时使用模式 C。

### 11.4 项目部署验收目标

项目应逐步验证以下部署能力：

- [ ] 能够在一台开发机器上启动完整系统，并通过本机浏览器访问。
- [ ] 本机开发模式下能够创建会议、加入会议并运行核心功能。
- [ ] 能够通过局域网访问入口，让其他设备打开会议页面。
- [ ] 局域网内其他设备能够完成摄像头和麦克风授权，并建立真实的音视频连接。
- [ ] 能够生成其他设备可访问的会议邀请链接。
- [ ] 能够在具有公网访问能力的单机环境中部署完整系统。
- [ ] 互联网用户能够通过 HTTPS 会议链接加入会议。
- [ ] 在目标规模下验证 5～10 人多人音视频通信，并记录实际运行表现。

部署能力的验证结果应结合技术验证和集成测试阶段的实验记录，不应仅以服务成功启动或页面能够打开作为验收依据。
