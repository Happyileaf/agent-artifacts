# 阶段 1—3：从三层应用到工程化单体与性能优化

本篇覆盖商城从第一个可运行版本，到能够由小团队稳定迭代并承受初步流量增长的过程。

## 阶段 1：最小可用商城——前端 + 后端 + 数据库

### 1.1 业务背景

团队刚开始做商城，只有商品列表、商品详情、用户注册登录、购物车、下单和基础支付能力。用户量不大，功能变化快，最重要的是尽快验证用户是否愿意购买。

此时不需要微服务、消息队列、分布式缓存或容器编排。一个前端应用、一个后端应用和一个关系型数据库，通常足以完成业务闭环。

### 1.2 最初的架构

\`\`\`mermaid
flowchart LR
    U["用户浏览器 / App"] --> FE["前端应用"]
    FE -->|"HTTP / HTTPS"| API["后端应用"]
    API --> DB[("关系型数据库")]
    API --> PAY["第三方支付平台"]
\`\`\`

典型技术栈：

| 层次 | 可选技术 | 选择原因 |
|---|---|---|
| Web 前端 | Vue / React | 构建商品、购物车和订单界面 |
| 移动端 | H5 / 小程序（按需） | 覆盖移动用户 |
| 后端 | Node.js / Java / Go / Python 等 | 提供 API 和业务规则 |
| 数据库 | MySQL / PostgreSQL | 事务、关联查询、约束和持久化 |
| 文件 | 本地磁盘（开发或早期小规模） | 暂存商品图片等文件 |
| 部署 | 一台云主机或简单托管服务 | 降低初期运维负担 |

### 1.3 代码如何组织

最初可以是简单的单体项目：

\`\`\`text
mall/
├── frontend/
└── backend/
    ├── routes/
    ├── controllers/
    ├── services/
    ├── repositories/
    ├── models/
    └── config/
\`\`\`

一个请求大致经过：

1. Controller 接收 HTTP 请求并校验输入。
2. Service 执行业务规则，例如校验商品是否可售。
3. Repository/DAO 访问数据库。
4. Controller 将结果转换为 HTTP 响应。

分层不需要过度复杂，但应避免把所有 SQL、业务判断和 HTTP 处理全部写在路由函数里。

### 1.4 一笔订单如何创建

简化后的同步流程：

\`\`\`mermaid
sequenceDiagram
    participant B as 浏览器
    participant A as 后端
    participant D as 数据库
    B->>A: POST /orders
    A->>D: 开启事务
    A->>D: 查询商品、价格和库存
    A->>D: 创建订单及订单明细
    A->>D: 扣减库存（条件更新）
    A->>D: 提交事务
    A-->>B: 返回待支付订单
\`\`\`

实际支付通常不能简单地放在数据库事务内部等待第三方网络调用。可以先创建待支付订单，再由用户发起支付；支付结果通过第三方回调更新订单状态。

库存扣减需要使用带条件的原子更新或锁，不能采用“先查库存、应用层判断、再无条件更新”的方式，否则并发下可能超卖。

### 1.5 数据库先承担什么职责

关系型数据库是系统的事实数据来源，保存用户、商品、订单、订单明细、支付记录和库存等数据。

例如：

- orders：订单主表，记录用户、金额、状态、创建时间。
- order_items：订单明细，记录商品快照、购买数量和成交价格。
- products / skus：商品及 SKU。
- inventory：库存数量。
- payments：支付单和支付状态。

订单明细需要保存下单时的商品名称、价格等快照，不能只关联当前商品信息，否则商品改名或改价后历史订单会发生变化。

### 1.6 部署方式

最简单时可以把前端静态文件和后端进程部署在一台机器，数据库也可能暂时在同一台机器。进入真实生产环境后，至少应考虑数据库备份、访问控制、HTTPS、日志和进程守护。

\`\`\`mermaid
flowchart TB
    subgraph Host["初期部署环境"]
      WEB["静态前端 / Web Server"]
      APP["后端进程"]
      DB[("数据库")]
      WEB --> APP
      APP --> DB
    end
    USER["用户"] --> WEB
\`\`\`

### 1.7 这个阶段的边界

**当前方案足够好的信号：**
- 团队人数少，代码改动集中。
- 业务模型和流程还在快速验证。
- 数据量和流量在单机能力范围内。
- 单次发布和回滚简单。
- 数据库查询和事务能够满足需求。

**开始出现的信号：**
- 功能增加后，改一个业务经常影响其他业务。
- 多人开发频繁冲突，测试困难。
- 发布风险逐渐增加。
- 商品图片等静态资源占用应用机器带宽和磁盘。
- 数据库慢查询开始影响用户体验。

不要因为应用只有一个部署单元就认为架构不成熟。对早期商城而言，简单单体往往是最经济的选择。

## 阶段 2：单体工程化——让系统可以持续开发

### 2.1 业务背景

商城上线后，陆续增加优惠券、退款、会员等级、订单售后和运营后台。开发人员从两三人增长到一个小团队。

问题不再是“能不能实现功能”，而是：
- 商品逻辑和订单逻辑互相调用，改动影响范围不可预测。
- Controller 越来越臃肿，业务规则散落在各处。
- 数据库访问方式不统一。
- 缺少自动化测试，修改后只能手工回归。
- 配置、日志和异常处理各自为政。

这时最需要的是工程化和模块边界，而不是立即拆分成多个独立服务。

### 2.2 从简单单体到分层、模块化单体

\`\`\`mermaid
flowchart TB
    subgraph App["一个可部署的后端应用"]
      API["API / Controller 层"]
      APP["应用服务层"]
      DOMAIN["领域 / 业务模块"]
      INFRA["基础设施适配层"]
      API --> APP
      APP --> DOMAIN
      DOMAIN --> INFRA
    end
    DB[("关系型数据库")] --- INFRA
    CACHE["外部依赖（按需）"] --- INFRA
\`\`\`

推荐先按业务模块组织代码，而不是只按技术类型堆积文件：

\`\`\`text
backend/
├── modules/
│   ├── user/
│   ├── catalog/
│   ├── cart/
│   ├── order/
│   ├── inventory/
│   ├── payment/
│   └── promotion/
├── shared/
├── infrastructure/
└── bootstrap/
\`\`\`

每个模块内部可以再按 controller、application、domain、infrastructure 等职责组织。项目规模较小时不必机械套用完整 DDD 分层。

### 2.3 工程能力逐步补齐

| 业务/团队问题 | 工程化能力 | 解决效果 |
|---|---|---|
| 输入格式不一致 | 参数校验、统一 API 契约 | 降低接口歧义 |
| 异常响应各不相同 | 统一异常处理和错误码 | 前端可稳定处理错误 |
| 线上问题难复现 | 结构化日志、请求 ID | 串联一次请求 |
| 改动容易引入回归 | 单元测试、集成测试 | 提高变更信心 |
| 配置散落代码 | 环境配置、密钥管理 | 区分开发、测试、生产 |
| 发布依赖人工操作 | CI/CD | 可重复构建和部署 |
| 数据结构变化危险 | 数据库迁移脚本 | 版本化管理 Schema |
| 多人协作冲突 | Code Review、模块所有权 | 明确变更责任 |

### 2.4 技术栈可能如何变化

后端语言和框架不一定变化。比如继续使用 Node.js + NestJS、Java + Spring Boot 或 Go + Gin，重点是把代码组织、测试和发布方式建立起来。

可以增加：
- ORM 或 SQL Mapper（例如 Prisma、TypeORM、MyBatis，按团队习惯）。
- OpenAPI 等接口描述。
- Jest、JUnit、Go test 等测试工具。
- GitHub Actions、GitLab CI、Jenkins 等 CI/CD。
- Docker（当环境一致性或部署需要时）。

### 2.5 为什么不直接微服务

因为代码耦合并不必然需要网络隔离。模块化单体可以在一个进程内保持明确的业务边界，调用成本低、事务简单、调试方便。

如果模块边界尚未稳定，直接拆成多个服务，只会把代码耦合转化为网络耦合和分布式数据问题。

### 2.6 阶段验收

- 模块职责和依赖方向清楚。
- 关键交易链路有自动化测试。
- 配置和密钥不写死在代码中。
- 数据库变更可追踪、可回滚或有前向修复方案。
- 发布过程可重复，生产问题可以通过日志定位。

## 阶段 3：单体性能优化——缓存、索引、对象存储与 CDN

### 3.1 业务背景

商城推广后，商品浏览量迅速增长。商品详情和类目页访问频繁，但商品数据变化相对较少。数据库 CPU 升高，商品列表查询变慢；商品图片又消耗大量应用服务器带宽。

此时先分析请求和数据库指标，而不是直接增加一堆中间件。

### 3.2 第一步：数据库诊断与查询优化

先做：
- 查看慢查询和执行计划。
- 为真实查询条件建立合适索引。
- 避免无必要的全表扫描和 N+1 查询。
- 控制返回字段和分页方式。
- 检查连接池、事务范围和锁等待。
- 对统计报表和在线交易查询做负载隔离评估。

索引不是越多越好。索引会占用空间，并增加写入、更新和维护成本。

### 3.3 第二步：引入缓存

商品详情是典型的高频读、相对低频写数据，可以将读取结果缓存到 Redis 等缓存中。

\`\`\`mermaid
flowchart LR
    U["用户请求"] --> API["商城后端"]
    API --> C{"缓存命中？"}
    C -->|"是"| R["返回缓存"]
    C -->|"否"| DB[("数据库")]
    DB --> API
    API -->|"写入缓存"| C
    R --> U
\`\`\`

常见模式是 Cache Aside：
1. 读取时先查缓存。
2. 未命中则查数据库。
3. 将结果写入缓存并设置 TTL。
4. 更新数据库后失效对应缓存。

必须考虑缓存穿透、击穿、雪崩、热点 Key、缓存与数据库短暂不一致等问题。缓存通常是加速层，不应在没有明确设计的情况下成为唯一事实来源。

### 3.4 第三步：静态文件独立存储

商品图片、详情页图片和用户上传文件不应长期依赖应用服务器本地磁盘。应用实例可能扩缩容或替换，本地文件不容易共享和备份。

可以将文件放到对象存储（如 S3 兼容服务、云厂商对象存储），通过 CDN 分发：

\`\`\`mermaid
flowchart LR
    ADMIN["运营后台上传"] --> APP["商城后端"]
    APP --> OSS[("对象存储")]
    USER["用户浏览器"] --> CDN["CDN 边缘节点"]
    CDN --> OSS
\`\`\`

后端负责权限校验、生成上传凭证或签名 URL；大文件可由客户端直传对象存储。对象存储负责持久化，CDN 负责就近分发和缓存。

### 3.5 第四步：按需增加读写分离

当数据库读负载明显高于写负载，且查询优化、缓存仍无法满足需求时，可以评估主从复制：

- 主库承接写入。
- 只读副本承接允许延迟的查询。
- 关键读请求仍走主库，避免复制延迟造成刚写入的数据读不到。

读写分离会引入复制延迟、读路由和故障切换复杂度，不应仅因为流量增长就默认启用。

### 3.6 本阶段技术栈

| 能力 | 可能技术 | 引入依据 |
|---|---|---|
| 数据库分析 | 慢查询日志、EXPLAIN、监控 | 先找出真实瓶颈 |
| 缓存 | Redis | 高频读取、可接受短暂旧值 |
| 对象存储 | S3 / 云对象存储 | 文件持久化和应用解耦 |
| 静态加速 | CDN | 用户地域分散、静态访问量大 |
| 数据库扩展 | 只读副本 | 读压力持续高于单主库能力 |

### 3.7 阶段验收

- 关键 API 有延迟、错误率和吞吐量指标。
- 慢查询有明确治理结果。
- 缓存失效策略和 TTL 有设计。
- 文件存储不依赖单个应用实例。
- 读写分离的请求一致性要求被明确区分。

### 3.8 本篇小结

这一阶段仍然可以是一个单体后端。缓存、对象存储、CDN 和数据库副本是围绕具体资源瓶颈增加的外部能力，并不要求同时引入，更不意味着必须拆分业务服务。
