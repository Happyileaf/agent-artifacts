# 项目推进方案

> 项目：浏览器多人在线会议与实时聊天室（browser-meeting-chat）  
> 文档类型：项目生命周期规划  
> 状态：规划基线  
> 关联需求：[`product-requirements.md`](../product-requirements.md)

---

## 1. 文档目的

本文档定义项目从需求基线、技术调研、方案决策、架构设计、技术验证，到工程准备、产品开发、测试部署和最终总结的完整推进方式。

这里的“阶段”指整个项目生命周期中的阶段，不仅仅是编码和开发阶段。项目不应在技术方案尚未明确、关键风险尚未验证时直接进入完整开发。

本项目以学习和技术实践为主要目标，推进过程中应优先保证核心业务场景完整、技术原理可理解、实验结果可复现，避免引入与目标不相称的生产级复杂度。

## 2. 推进原则

1. **先理解，再决策，再实现**：先完成必要的技术调研，再进行技术选型和架构设计，最后通过 PoC 验证关键假设。
2. **阶段有明确出口**：每个阶段都需要明确交付物和进入下一阶段的条件，不能仅以“工作做过了”作为阶段完成依据。
3. **关键风险前置验证**：多人媒体通信、信令协商、重连、监控数据可获取性和部署网络条件，应尽量在正式开发前验证。
4. **以 PRD 为产品基线**：技术设计可以解释如何实现需求，但不能未经确认擅自改变产品行为和范围。
5. **控制项目复杂度**：优先采用成熟、可自行部署且适合学习和集成的方案；不为假想的生产级需求提前建设复杂基础设施。
6. **文档与实现同步演进**：技术决策、架构、协议和实验结论应及时记录；验证结果可能反向修正决策和设计。
7. **支持非连续推进**：项目可能分散在不同时间推进。每个阶段都应留下清晰的进度、结论、待办和下一步入口，方便恢复上下文。
8. **不预设固定工期**：按照阶段出口和实际验证结果推进，不为了赶排期跳过调研或验证。

## 3. 项目生命周期总览

| 阶段 | 名称 | 核心目标 | 主要出口 |
|---|---|---|---|
| 0 | 项目启动与需求基线 | 明确做什么、不做什么以及如何验收 | 需求基线可用于技术调研 |
| 1 | 技术调研与可行性分析 | 理解候选技术和关键约束 | 形成有依据的候选方案与风险清单 |
| 2 | 技术选型与方案决策 | 对核心技术做出明确选择 | 核心技术决策有记录 |
| 3 | 系统架构与详细设计 | 明确模块、流程、协议和数据关系 | 设计足以指导 PoC 和开发 |
| 4 | 技术验证与方案收敛 | 验证关键技术假设和部署可行性 | 关键风险得到验证，方案收敛 |
| 5 | 工程准备 | 建立可复现的开发工程基础 | 新环境可以按文档启动项目 |
| 6 | 产品开发与阶段性交付 | 按业务能力逐步实现 PRD | 核心需求实现并完成阶段检查 |
| 7 | 集成测试与部署验证 | 验证完整业务、网络和部署场景 | 核心验收通过，部署可复现 |
| 8 | 项目交付与技术总结 | 完成成果整理和学习沉淀 | 产品、文档和实验成果完整交付 |

整体顺序如下：

```text
项目启动与需求基线
        ↓
技术调研与可行性分析
        ↓
技术选型与方案决策
        ↓
系统架构与详细设计
        ↓
技术验证与方案收敛
        ↓
工程准备
        ↓
产品开发与阶段性交付
        ↓
集成测试与部署验证
        ↓
项目交付与技术总结
```

阶段之间允许反馈和回退。例如 PoC 发现 SFU 方案不满足目标时，应返回技术选型或架构设计阶段调整，而不是带着已知问题继续开发。

## 4. 各阶段工作内容

### 阶段 0：项目启动与需求基线

**目标**

将产品想法整理为明确、可追踪、可验收的需求输入。

**主要工作**

- 确认项目目标、用户场景和项目定位。
- 梳理创建会议、加入会议、设备准备、音视频、聊天、离开和重连等核心流程。
- 明确会议创建者与普通参与者的行为差异。
- 明确 5～10 人目标规模、10 人上限和 30 秒重连规则。
- 梳理功能需求、非功能需求、异常场景和验收标准。
- 明确项目不做的内容，避免后续无边界扩张。
- 建立需求检查清单，供设计、开发和测试阶段追踪。

**交付物**

- `product-requirements.md`：产品需求基线（已存在）。
- `requirement-checklist.md`：需求及验收检查清单。
- `project-scope.md`：范围和边界说明（如果需求基线中已有充分说明，可不重复拆分）。

**阶段出口**

- PRD 已确认，作为产品需求的唯一基线。
- 核心业务规则和验收场景明确。
- 技术调研能够以 PRD 为输入开展。

### 阶段 1：技术调研与可行性分析

**目标**

理解实现项目所需的技术原理、候选方案、适用条件和限制。本阶段以调研和比较为主，不急于锁定技术栈。

**主要调研方向**

1. **WebRTC 基础**
   - MediaStream、MediaTrack、RTCPeerConnection。
   - SDP Offer / Answer。
   - ICE、STUN、TURN、Candidate 和 Candidate Pair。
   - 浏览器媒体设备权限与安全上下文要求。
   - WebRTC Stats 及浏览器可观测性边界。

2. **多人音视频通信**
   - Mesh 与 SFU 的工作方式和差异。
   - 多人场景下的上行、下行带宽和资源消耗。
   - SFU 的媒体转发、订阅和发布模型。
   - 可自行部署的开源媒体服务器及其集成方式。

3. **实时信令**
   - WebSocket 等实时双向通信方式。
   - SDP、ICE Candidate 的交换过程。
   - 房间、参与者和连接状态的同步。
   - 断线、重连和重复消息等场景。

4. **实时聊天**
   - 消息发送和广播。
   - 消息顺序与在线成员范围。
   - 新成员不接收加入前消息的实现方式。

5. **技术监控**
   - 浏览器 WebRTC Stats 可获取的指标。
   - 连接、ICE、Candidate Pair 和媒体统计之间的关系。
   - 码率、丢包率等派生指标的计算条件。
   - 使用 SFU 时客户端和服务端各自能够观测到的信息边界。

6. **部署与网络**
   - macOS / Apple Silicon 环境下的本地运行方式。
   - Docker 与 Docker Compose 的适用性。
   - 局域网访问、HTTPS 和浏览器安全上下文。
   - 公网部署需要的域名、证书、端口和 UDP 连通性。
   - STUN / TURN 在不同网络环境中的作用。

**开源方案调研重点**

- 是否真正支持多人会议。
- 是否支持自行部署。
- 是否方便集成到现有 Web 项目。
- 媒体通信和信令能力如何划分。
- 是否提供可用的 SDK、API 和监控信息。
- 许可证及二次开发限制。
- 本地单机部署难度和资源要求。
- 项目活跃度、文档质量和维护情况。

**交付物**

- `research/webrtc-fundamentals.md`
- `research/multiparty-communication.md`
- `research/signaling-solutions.md`
- `research/open-source-solutions.md`
- `research/technical-risk-assessment.md`

以上文件按实际调研逐步建立，不要求在阶段开始时一次性创建空文件。

**阶段出口**

- 已理解主要技术机制和候选方案。
- 主要方案的适用条件、限制和成本有比较依据。
- 关键技术风险已经识别。
- 具备进入技术选型的足够信息。

### 阶段 2：技术选型与方案决策

**目标**

将调研结论转化为适用于本项目的明确技术决策。

**需要决策的内容**

- 前端框架、语言和构建工具。
- 服务端语言和框架。
- 多人媒体通信方案：Mesh 或 SFU。
- 是否采用现有开源 SFU / 实时通信平台。
- 信令由媒体平台提供还是由项目自行实现。
- 会议管理与参与者状态管理方式。
- 实时聊天的消息传递方式。
- STUN / TURN 的使用方案。
- 技术监控的数据来源和采集方式。
- 本机、局域网和公网的部署方式。

**决策要求**

- 优先选择能满足 PRD 且复杂度适中的方案。
- 对比方案时说明选择理由，而不只记录技术名称。
- 区分已确定决策、待验证假设和暂缓决策。
- 不提前引入当前阶段没有必要的数据库、消息队列或集群。
- 对重要决策使用 ADR（Architecture Decision Record）记录。

**交付物**

- `decisions/ADR-001-frontend-stack.md`
- `decisions/ADR-002-backend-stack.md`
- `decisions/ADR-003-media-communication.md`
- `decisions/ADR-004-signaling.md`
- `decisions/ADR-005-deployment.md`

编号和文件数量根据实际决策调整，不要求机械地拆分。

ADR 至少记录：背景与问题、候选方案、比较依据、最终选择、选择理由、限制、影响，以及仍需验证的事项。

**阶段出口**

- 核心技术选择已经明确。
- 重要取舍有记录且能够解释。
- 仍未验证的关键假设已进入 PoC 计划。
- 不存在阻碍架构设计的重大技术选择空缺。

### 阶段 3：系统架构与详细设计

**目标**

明确系统由哪些模块组成、模块之间如何协作，以及关键业务流程如何实现。

**主要设计内容**

1. **总体架构**
   - Web 前端、业务服务、信令能力、SFU 媒体服务、STUN / TURN 的职责和关系。
   - 单机部署时各组件的组织方式。
   - 客户端与服务端的通信边界。

2. **模块职责**
   - 会议创建和加入。
   - 参与者身份与状态。
   - 设备管理和媒体轨道。
   - 信令与媒体连接。
   - 实时聊天。
   - 会议生命周期和重连。
   - 技术监控。

3. **核心业务流程**
   - 创建会议。
   - 通过邀请链接加入。
   - 设备授权和准备。
   - 媒体连接建立。
   - 成员主动离开。
   - 普通成员意外断线和重连。
   - 创建者意外断线、等待和会议结束。
   - 实时聊天。

4. **通信协议**
   - 消息结构和类型。
   - 信令交互。
   - 成员状态事件。
   - 聊天消息。
   - 错误码和异常反馈。

5. **数据模型**
   - 会议。
   - 参与者。
   - 连接或媒体端点（根据最终方案确定）。
   - 聊天消息及其生命周期。

6. **技术监控设计**
   - 指标来源。
   - 采样和派生指标计算。
   - 连接与参与者关联方式。
   - 客户端和服务端监控边界。

7. **部署设计**
   - 三种运行模式的配置差异。
   - 服务监听地址和对外公布地址。
   - 端口、HTTPS、ICE 和 TURN 配置。
   - 本机与容器之间的网络关系。

**交付物**

- `architecture/overview.md`
- `architecture/module-design.md`
- `architecture/business-flows.md`
- `architecture/signaling-protocol.md`
- `architecture/data-model.md`
- `architecture/monitoring-design.md`
- 必要的 Draw.io 架构图、时序图和流程图。

按最终技术方案决定是否需要全部独立文档，避免为了目录完整而重复内容。

**阶段出口**

- 模块职责和边界明确。
- 核心业务流程有设计。
- 关键接口、消息和状态约定足以指导 PoC。
- 设计与 PRD 的需求能够对应。
- 未决问题已列明，不以模糊假设进入实现。

### 阶段 4：技术验证与方案收敛

**目标**

通过小规模、可独立运行的 PoC 验证架构设计中的关键假设。不能只验证某个开源项目能够启动，还要验证它是否满足本项目的业务和部署要求。

**重点验证项**

1. **多人媒体通信 PoC**
   - 验证所选方案的发布、订阅和媒体转发流程。
   - 验证多人加入、离开和媒体状态变化。
   - 观察 5 人及目标 10 人场景下的基本表现。

2. **Mesh / SFU 方案验证**
   - 如调研阶段仍存在明显取舍，通过实验比较连接数量、媒体转发方式和资源开销。
   - 记录选择方案的理由，不为追求实验数量而重复验证已充分确定的结论。

3. **信令 PoC**
   - 验证必要的连接协商流程。
   - 验证 SDP、ICE 信息交换和连接状态变化。
   - 明确媒体平台与自建业务服务之间的职责边界。

4. **重连 PoC**
   - 验证参与者身份恢复。
   - 验证连接断开后的重新建立。
   - 验证创建者等待期间的会议行为是否可实现。

5. **监控 PoC**
   - 验证 PRD 中要求的指标是否能够从实际运行环境获取。
   - 验证 WebRTC Stats 采样和派生指标计算。
   - 对无法获取或只能从服务端获取的指标明确标注边界。

6. **单机完整运行 PoC**
   - 在开发者的 MacBook（Apple Silicon M5、32GB 统一内存）上尝试运行必要组件。
   - 验证服务能够在一台机器上完整启动。
   - 评估容器镜像和依赖对 Apple Silicon 的兼容性。
   - 记录 CPU、内存、网络和持续运行情况。MacBook Air 的持续负载表现应以实测为准。

7. **三种部署模式 PoC**
   - 模式 A：本机通过 localhost 访问。
   - 模式 B：其他局域网设备通过可访问地址加入，验证 HTTPS、信令和媒体链路。
   - 模式 C：在具备公网访问条件的单机环境验证公开 HTTPS 链接、媒体 UDP 和必要的 TURN 中继。
   - 三种模式使用同一套应用代码，重点验证配置和网络差异。

**交付物**

- `poc/README.md`
- `poc/experiments/` 下的实验代码和记录。
- 实验结果、性能观测和问题清单。
- 更新后的 ADR 与架构文档。

**阶段出口**

- 核心技术假设已通过实验验证，或已明确失败原因和替代方案。
- 单机完整运行路径可行。
- 关键部署模式的网络要求已明确。
- PRD 核心监控指标的数据来源和限制清楚。
- 方案已根据 PoC 结果收敛；如未通过，应返回阶段 2 或阶段 3 调整。

### 阶段 5：工程准备

**目标**

建立正式开发所需的工程基础，不在这一阶段提前实现全部产品功能。

**主要工作**

- 初始化项目代码仓库和目录结构。
- 初始化前端、后端及必要服务工程。
- 建立本地开发启动方式。
- 根据已验证的方案准备 Docker Compose 或其他必要运行配置。
- 配置代码格式化、静态检查和基础测试。
- 配置基础 CI。
- 准备环境变量和敏感配置管理。
- 编写开发说明和任务清单。
- 确保关键依赖在目标开发环境可运行。

**交付物**

- 可运行的项目骨架。
- 本地开发环境说明。
- 基础工程规范。
- 基础 CI 和测试入口。
- 开发任务清单。

**阶段出口**

- 新环境能够按照文档完成必要依赖准备并启动项目。
- 工程结构与已确认的架构设计一致。
- 基础检查和测试能够运行。
- 开发不再依赖未记录的个人机器状态。

### 阶段 6：产品开发与阶段性交付

**目标**

按照业务能力逐步实现 PRD，而不是将所有功能堆到一个开发阶段末尾。

**建议实施顺序**

1. **会议基础能力**
   - 创建会议。
   - 通过邀请链接加入。
   - 昵称和参与者身份。
   - 会议人数限制。

2. **设备准备**
   - 摄像头和麦克风权限。
   - 设备选择与本地预览。
   - 设备不可用和权限异常提示。

3. **音视频通信**
   - 建立媒体连接。
   - 展示本地和远端媒体。
   - 音视频开关与状态同步。

4. **多人会议**
   - 多人加入、发布和订阅媒体。
   - 参会者列表。
   - 5～10 人场景验证。

5. **会议生命周期**
   - 主动离开。
   - 普通成员意外断线与重连。
   - 创建者意外断线与会议结束。
   - 人数名额和等待状态处理。

6. **实时聊天**
   - 发送和接收消息。
   - 在线成员消息同步。
   - 新加入成员不接收加入前消息。

7. **WebRTC 技术监控**
   - 会议级、连接级和媒体级信息。
   - 真实状态与 WebRTC Stats。
   - 指标计算和关键事件时间线。

每个子阶段都应进行基本自测，并对照需求检查清单更新完成情况。若前序功能的实现暴露出架构问题，应及时回到设计阶段修正，不应仅通过局部补丁掩盖问题。

**交付物**

- 可运行的阶段性产品。
- 与实现同步更新的技术文档。
- 需求检查清单和阶段测试记录。
- 需要时更新的 ADR 和架构设计。

**阶段出口**

- PRD 中的核心功能均已实现。
- 主要业务流程可以端到端运行。
- 未完成项、已知问题和限制均有记录。

### 阶段 7：集成测试与部署验证

**目标**

**主要测试场景**

**部署验证**

- 本机开发模式能够按文档启动。

- 公网部署模式能够通过 HTTPS 链接加入。
- 必要端口、媒体地址和 TURN 配置有明确说明。
- 部署过程可重复执行，不依赖未记录的手工操作。

**交付物**

- 测试报告。
- 问题清单和修复记录。
- 部署文档。
- 可运行的完整系统。
- 三种部署模式的验证结果。

**阶段出口**

- PRD 核心验收场景通过。
- 重大问题已解决，或其影响和限制已明确记录。
- 至少完成项目要求的部署模式验证；未完成项有明确原因和后续安排。

## 6. 进度管理方式

由于项目会分散在不同时间推进，需要维护一个简洁、持续更新的进度入口。

建议使用 `planning/project-progress.md` 记录：

- 当前所处阶段。
- 当前阶段目标。
- 已完成的工作和交付物链接。
- 已确认的决策。
- 尚未解决的问题和风险。
- 下一步最具体的行动。
- 是否存在阻塞，以及需要用户确认的事项。

`planning/task-list.md` 用于管理当前阶段的具体任务，不需要提前把整个项目拆成大量细碎任务。

每次阶段切换时更新进度文档；每次暂停时至少记录当前结论、未完成事项和下一步入口。恢复项目时先阅读 PRD、项目推进方案和进度记录，再继续执行，避免重复讨论或基于过期假设推进。
