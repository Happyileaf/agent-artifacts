# 贯穿各阶段的工程能力与技术栈地图

本篇将前面分阶段出现的能力放在一起，说明它们如何协同，以及在真实项目中如何选择演化顺序。

## 1. 技术栈全景地图

| 技术领域 | 早期常见方案 | 规模扩大后的可选方案 | 主要解决的问题 |
|---|---|---|---|
| 前端 | Vue / React | 多端应用、微前端（确有组织需求时） | 用户交互与多渠道访问 |
| 后端 | 单体应用 | 模块化单体、微服务 | 业务处理与服务边界 |
| API | REST / JSON | REST、gRPC、事件契约 | 客户端和服务间协作 |
| 关系型数据库 | MySQL / PostgreSQL 单实例 | 高可用、只读副本、分区、分片 | 事务数据持久化 |
| 缓存 | 进程内缓存 | Redis、分布式缓存集群 | 降低热点读取压力 |
| 消息 | 无或简单任务 | RabbitMQ、Kafka、云消息服务 | 异步解耦、缓冲和事件分发 |
| 搜索 | 数据库查询 | Elasticsearch / OpenSearch | 全文检索和复杂筛选 |
| 文件 | 本地磁盘 | 对象存储 + CDN | 文件持久化和分发 |
| 定时任务 | Cron / 应用任务 | 任务调度平台、延迟队列 | 定时和批处理 |
| 部署 | 进程 / 虚拟机 | Docker、Kubernetes、托管容器 | 一致交付、调度和扩缩容 |
| 配置 | 环境变量 / 配置文件 | 集中配置、密钥管理 | 环境隔离和安全管理 |
| 监控 | 日志、主机监控 | Metrics、Logs、Traces、告警平台 | 发现和定位问题 |
| 数据分析 | 业务库报表 | CDC、ETL、数据仓库 | 分析负载与交易负载隔离 |
| 安全 | 登录鉴权、HTTPS | 零信任、服务身份、审计、供应链安全 | 降低攻击和误用风险 |

同一领域可能有多种实现。技术选型要考虑团队能力、托管能力、生态、成本、合规、迁移难度和故障恢复方式。

## 2. 一笔订单在不同架构中的变化

### 2.1 单体阶段

订单、库存、支付记录可能在同一个后端应用中处理。订单与库存可以使用同一个数据库事务，但第三方支付网络调用应在事务外进行，并通过支付回调更新状态。

### 2.2 异步阶段

订单事务提交后，通过 Outbox 发布事件。通知、积分和统计异步消费。消息可能重复，因此消费者必须幂等。

### 2.3 微服务阶段

订单、库存和支付拥有独立的数据存储。下单流程变成跨服务协作，需要 Saga、状态机、超时、重试、补偿和人工处理路径。

### 2.4 大规模阶段

秒杀活动可能加入准入控制、库存配额、排队和削峰。搜索索引和分析数据通过事件异步更新，不再直接依赖交易库完成所有查询。

## 3. 一致性与可靠性：不要把所有问题都叫分布式事务

| 场景 | 合适的思路 |
|---|---|
| 单库内订单和订单明细 | 数据库 ACID 事务 |
| 单库内库存扣减 | 条件更新、锁、约束 |
| 数据库提交后发布事件 | Transactional Outbox / CDC |
| 消息重复投递 | 幂等消费、唯一约束 |
| 跨服务订单流程 | Saga、状态机、补偿 |
| 搜索索引更新 | 事件驱动最终一致 |
| 缓存更新 | Cache Aside、失效策略、TTL |
| 第三方支付回调 | 验签、幂等、状态校验、对账 |
| 外部服务暂时不可用 | 超时、有限重试、熔断、隔离 |
| 数据丢失或地域故障 | 备份、恢复演练、灾备 |

关键原则：
- 重试必须有上限、退避策略和幂等保障。
- 超时不代表操作一定失败；调用方需要查询或对账。
- 补偿是新的业务动作，不是数据库事务回滚。
- 最终一致性必须有可观测、可重放和对账机制。
- 对账是发现和修复系统间差异的重要手段，不是可有可无的报表功能。

## 4. 关键非功能能力的成熟路径

### 4.1 安全

1. 早期：HTTPS、密码安全存储、基本认证授权。
2. 工程化：权限模型、输入校验、审计日志、密钥管理。
3. 服务化：服务身份、服务间授权、网络隔离。
4. 大规模：集中安全监测、供应链安全、数据分类分级、合规流程。

### 4.2 可观测性

1. 早期：应用日志、错误日志、健康检查。
2. 多实例：集中日志、请求 ID、基础指标。
3. 微服务：分布式追踪、服务依赖拓扑、队列监控。
4. 成熟阶段：SLO、错误预算、业务指标、告警降噪和自动化响应。

### 4.3 测试

- 单元测试：验证单个函数或领域规则。
- 集成测试：验证数据库、缓存、消息等依赖协作。
- 契约测试：验证服务接口兼容性。
- 端到端测试：验证关键用户流程。
- 性能测试：验证容量和峰值行为。
- 混沌/故障演练：验证依赖故障时的系统行为。

测试类型不是越多越好，应覆盖风险最高的业务路径。商城最值得优先保障的是下单、库存、支付、退款和订单状态流转。

### 4.4 发布与数据库变更

应用发布和数据库 Schema 变更必须协同设计：
- 优先采用向前兼容的扩展—迁移—收缩模式。
- 新旧应用版本共存期间，字段和接口必须兼容。
- 大表变更需要评估锁、复制延迟和回填时间。
- 回滚应用不一定能回滚数据，必要时准备前向修复。
- 对高风险变更设置灰度、观测和停止条件。

## 5. 常见误区

### 误区 1：用户量一大就必须微服务

流量大不等于模块必须拆分。先看瓶颈是否能通过索引、缓存、读写分离、应用横向扩容解决。

### 误区 2：用了 Redis 就算高性能架构

缓存可能引入一致性、热点、穿透、雪崩和数据恢复问题。缓存命中率、回源压力和失效策略都要监控。

### 误区 3：用了消息队列就实现了异步可靠

还要解决事务消息、重复消费、失败重试、死信、积压、顺序和消息回放。

### 误区 4：微服务等于每个服务一套独立基础设施

服务可以共享平台和托管基础设施，但必须保持数据所有权和访问边界。物理隔离程度取决于安全、性能和可靠性需求。

### 误区 5：Kubernetes 是大型系统的必选项

Kubernetes 解决的是容器编排问题，不会自动解决业务架构、数据一致性和团队协作问题。托管平台或更简单的运行环境可能更合适。

### 误区 6：多活一定比主备先进

多活会带来跨地域写入、冲突处理、路由和故障切换复杂度。若业务不能接受数据冲突，主备或按地域分区可能更合适。

### 误区 7：技术栈越新越成熟

成熟度来自稳定的业务边界、可验证的可靠性、清晰的数据责任和有效的交付流程，而不是技术名称。

## 6. 架构演化决策清单

每次准备引入新技术或拆分系统前，先回答：

1. **业务问题是什么？** 用真实用户场景或业务指标描述，而不是“想上某技术”。
2. **问题是否已被测量？** 是否有延迟、错误率、容量、积压或交付效率数据？
3. **当前方案的上限在哪里？** 是否已完成低成本优化？
4. **候选方案解决哪个瓶颈？** 预期收益如何验证？
5. **会引入什么复杂度？** 数据一致性、运维、故障模式和成本分别是什么？
6. **是否可以渐进实施？** 能否先做局部试点、灰度或模块化改造？
7. **失败时如何恢复？** 有无回滚、补偿、备份和人工处理流程？
8. **谁负责长期运行？** 团队是否有能力监控、升级和排障？

## 7. 一个实用的演化顺序

对大多数从零开始的商城，下面的顺序通常比一次性建设全套基础设施更稳妥：

1. 先跑通核心交易闭环：前端、后端、关系型数据库。
2. 做好模块边界、测试、日志、配置和自动化发布。
3. 基于监控优化数据库查询，再按需增加缓存、对象存储和 CDN。
4. 将通知、统计等非核心操作异步化，建立消息可靠性和幂等机制。
5. 先在单体内部明确领域边界和数据所有权。
6. 只有当独立部署、扩缩容或团队协作收益明确时，再逐步拆分服务。
7. 根据真实数据规模和访问模式评估读写分离、分片、搜索和数据平台。
8. 当服务数量和交付复杂度足够高时，再引入容器编排和平台工程。
9. 按业务损失和恢复目标建设高可用、灾备、安全和成本治理。

## 8. 结语

服务端架构演化的本质，是不断调整系统的复杂度分布：

- 早期把复杂度放在单体应用内部，换取简单部署和快速验证。
- 业务复杂后，通过模块和领域边界管理代码与团队协作。
- 流量和数据增长后，按瓶颈增加缓存、消息、搜索和数据扩展能力。
- 独立交付和扩缩容成为刚需后，才承担分布式系统的成本。
- 系统成为关键业务基础设施后，再投资于高可用、灾备、安全、可观测性和平台化。

**好的架构不是预先猜中未来所有需求，而是在当前阶段用足够简单的方案解决真实问题，同时让下一次变化有清晰的切入点。**
